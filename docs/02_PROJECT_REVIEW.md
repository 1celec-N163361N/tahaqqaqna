# 02 — مراجعة مشروع «تحققنا» وتحليل العيوب (PROJECT REVIEW)

> كل بند أدناه **مُختبر فعليًا** في المتصفح بتاريخ 2026-10-20. لم يُسجَّل أي شيء كـ«يعمل» دون تنفيذ المسار كاملًا.
> الالتزام بالشفافية: الموقع نفسه يعلن في كل صفحة أنه **نموذج تجريبي/محاكاة** — وهذا وصف صحيح ودقيق، ونؤكده هنا.

---

## 1. ما تم تنفيذه فعليًا في الموقع (مُحقّق)

### أ. الصفحة الرئيسية
- عنوان واضح: «إصدار الهوية الوطنية لأول مرة عن بُعد» + شريط إشعار: «خدمة مقترحة ضمن المسابقة — نموذج تجريبي يخضع للتكامل والاعتماد الرسمي».
- فيديو تعريفي 31 ثانية (مشاهد مولّدة بالذكاء الاصطناعي + تعليق صوتي) مع أزرار تشغيل/تخطي/كتم.
- **مُبدّل سيناريوهات العرض** (ميزة قوية نادرًا ما توجد عند الفرق الأخرى): `نجاح الرحلة` / `مشكلة بالصورة` / `عدم مطابقة الوجه`.
- زر «إعادة بدء التجربة»، زر مساعدة عائم، تذييل بنصوص إخلاء مسؤولية واضحة.
- تصميم عربي RTL كامل بهوية بصرية موحدة (أخضر داكن/أبيض) واحترافي.

### ب. رحلة التحقق (7 خطوات بمؤشر تقدّم)
| # | الخطوة | ما يعمل فعليًا |
|---|---|---|
| 1 | **التحقق من ولي الأمر** | دخول أبشر تجريبي ← شاشة **نفاذ واقعية** (اختيار الرقم المطابق 24) ← «محاكاة الموافقة/الانتهاء» ← **زر «محاكاة انتهاء الطلب»** يعمل ويعرض رسالة انتهاء صلاحية مع إعادة إرسال ✅ |
| 2 | **اختيار التابع** | 3 تابعين تجريبيين (أرقام سجل مقنّعة 10•••••234) + تأكيد اختيار ✅ |
| 3 | **الموافقة والاستعداد** | قائمة تحقق + **مربع موافقة يتحكم بتفعيل زر المتابعة** (لا يمكن التقدم دون موافقة) + إفصاح خصوصية صريح: «لا يتم رفع الصور أو بث الكاميرا إلى خادم» ✅ |
| 4 | **صورة الهوية** | رفع/استخدام صورة تجريبية ← **أداة قص وتكبير** (إخراج 800×1200 بنسبة 2:3) ← **فحص جودة محاكى** (إضاءة/وضوح/إطار) يمنع التقدم عند الفشل مع سبب واضح ✅ |
| 5 | **التحقق المرئي** | **كاميرا حقيقية (getUserMedia)** ← 3 تحديات حركية عشوائية (مثل: «حرّك رأسك قليلًا إلى اليسار») × 3 محاولات ← إرشادات تمثيلية أثناء التحدي ← معالجة رفض إذن الكاميرا برسالة واضحة وإعادة محاولة ✅ |
| 6 | **نتيجة التحقق** | بطاقات حالة (مطابقة وجه/حيوية/تزييف/استيفاء متطلبات) + **تنبيه صدق مهم**: «مطابقة الوجه لا تكفي وحدها لاعتماد الهوية؛ يلزم التحقق من ارتباط المتقدم بالسجل الحكومي» ✅ |
| 7 | **مراجعة الطلب** | «تم اعتماد إصدار الهوية» برقم طلب (TQ-2026-00419) + نموذج توصيل تجريبي عبر سبل مع تنبيه بعدم التنفيذ الحقيقي ✅ |

### ج. نقاط القوة الحقيقية (تدعم التميّز)
1. **مسيرة كاملة بلا فجوات**: من نفاش إلى إصدار الهوية — رحلة واحدة متصلة.
2. **سيناريوهات عرض مدمجة**: إظهار حالة الرفض وسببها للمحكّم مباشرة — أقوى من الشرح الشفهي.
3. **صدق تقني نموذجي**: تنبيهات «محاكاة/تجريبي» في كل خطوة + إقرار بأن التحقق البصري لا يُغني عن ربط السجل الحكومي — يبني ثقة اللجنة ولا يبالغ.
4. **بوابة موافقة حقيقية**: لا تقدم دون موافقة صريحة، مع نص يوضح عدم الخزن/الرفع للسيرفر.
5. **معالجة أخطاء مُختبرة**: انتهاء الجلسة، رفض الكاميرا، صورة غير مطابقة، جودة الصورة — أربع مسارات فشل تعمل جميعها.

### ما لم يكن عيبًا (شُكِّت ثم دُحضت بالفحص)
- ❌ «الزر معطّل بلا سبب» — كل أزرار التقدم المعطّلة معطّلة بسبب بوابة منطقية (موافقة/فحص صورة) وليست خطأ.
- ❌ «بيانات مزيفة تُعرض كحقيقية» — النصوص تقول صراحة «محاكاة/تجريبي» في كل خطوة.
- ❌ «الرفض بلا سبب» — الرفض يظهر دائمًا مع سبب وتوجيه («ملامح الوجه غير واضحة… أعد رفعها»).

## 3. المخاطر غير التقنية

| الخطر | الاحتمال | المعالجة |
|---|---|---|
| نوم الخوادم لحظة العرض (D1) | عالية | إيقاظ 5 دقائق قبل + لقطات شاشة بديلة (مجلد screenshots) |
| شبكة القاعة بطيئة/مقيّدة | متوسطة | تسجيل فيديو للرحلة كاملة كخطة بديلة (موصى به — انظر 04) |
| رفض إذن الكاميرا على جهاز العرض | متوسطة | تجهيز الإذن مسبقًا + خطة المحاكاة المقترحة (D3) |
| السيناريو المختار يُفقد (D2) | عالية لو حصل | في العرض: اختر السيناريو ثم «تخطي» مباشرة — لا تضغط «إعادة بدء التجربة» |

## 4. الخلاصة

«تحققنا» حل تقني حقيقي يعمل، لا واجهة فارغة. نقاط الضعف كلها **قابلة للمعالجة بسكربتات عرض وخطة تشغيل**، وليست ثقوبًا في المنطق. الأولوية القصوى الآن: **عرض محكّمين مُعاد بنائه** (ال chريحة 7 فارغة حاليًا) + **خطة تشغيل للإيقاظ** — وهذا ما نُفّذ في هذا المجلد.
